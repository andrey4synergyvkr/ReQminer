# Обзор логической модели данных

## 1. Введение

### 1.1. Назначение документа
Документ содержит текстовое описание 
логической доменной модели данных для управления требованиями в Scrum или аналогичном SDLC.

Документ дополняет UML-диаграммы и фиксирует семантику сущностей, атрибутов, связей и бизнес-правил.

### 1.2. Термины и сокращения

| Термин | Описание |

| Сущность | Класс домена, представляющий бизнес-объект. |

## 2. Обзор модели данных
### 2.1. Границы модели
Модель описывает домен управления требованиями и их жизненным циклом в рамках Scrum или аналогичного SDLC.

Включено:
- иерархия функциональных требований;
- нефункциональные требования и цели качества;
- атрибуты качества;
- критерии приема;
- критерии завершенности;
- риски;
- зависимости между требованиями;
- трассируемость требований;
- валидация требований;
- доменный глоссарий;
- ограничения, влияющие на требования, цели качества, риски и технические истории.

Не включено:
- детали технической реализации;
- другие элементы SDLC, напрямую не относящиеся к работе с требованиями;

### 2.2. Основные допущения и ограничения
- Требования могут создаваться вручную или извлекаться автоматически из входящих Markdown-документов.
- Перед LLM-анализом Markdown-документы нарезаются на фрагменты.
- Каждый фрагмент снабжается метаданными для трассировки: позиция в документе, иерархия заголовков, хеш содержимого, индекс фрагмента.
- Результаты автоматического извлечения — это требования в статусе `EXTRACTED`; они проходят ручную проверку перед подтверждением.
- Для требований могут храниться коэффициенты уверенности и история их изменений (`ConfidenceAssessment`).
- Подтверждение требования экспертом фиксируется в атрибутах `reviewedBy`, `reviewDecision`, `reviewComment`.
- Термины, используемые в функциональных требованиях, могут быть связаны с доменным глоссарием.
- Ограничения отделены от требований и не являются функциональными требованиями.
- Коэффициенты уверенности интерпретируются как вероятностные оценки в диапазоне от 0 до 1.
- Модель не задаёт физическое хранение данных, форматы файлов и конкретные технологии реализации.

## 3. Описание сущностей
Примечания к разделу:
- Для всех сущностей предполагается общий атрибут `id` — уникальный идентификатор экземпляра. В таблицах атрибутов он не повторяется.
- Идентификация экземпляров выполняется по `id`, если не указано иное.
- Правила эквивалентности экземпляров не определены, если не указано иное.
- Источник трассировки для всех сущностей — рабочая постановка задачи при разработке модели.
- Стереотипы и пакеты UML вынесены в Приложение A.
- Статусные модели указаны только для сущностей с выраженным жизненным циклом.

### 3.1. `Requirement`

Абстрактная базовая сущность для требований. Включает поля, ранее принадлежавшие валидационному конвейеру (`RequirementCandidate`, `ExtractionRun`, `ManualConfirmation`).

**Определение.**  
Требование — это фиксируемое положение о системе, которое подлежит проверке, подтверждению, трассировке и управлению жизненным циклом.

**Атрибуты**

| # | Имя атрибута        | Тип данных | Обязательный | Описание                                                |
|---|---------------------|------------|--------------|---------------------------------------------------------|
| 1 | `title`             | `String`   | Да           | Краткое название требования                             |
| 2 | `description`       | `String`   | Нет          | Описание требования                                     |
| 3 | `rationale`         | `String`   | Нет          | Обоснование требования                                  |
| 4 | `priority`          | `String`   | Нет          | Приоритет требования                                    |
| 5 | `lifecycleStatus`   | `Enum`     | Да           | Статус жизненного цикла: от EXTRACTED до DEPRECATED     |
| 6 | `source`            | `String`   | Нет          | Источник требования                                     |
| 7 | `estimate`          | `String`   | Нет          | Оценка требования                                       |
| 8 | `isMandatory`       | `Boolean`  | Нет          | Признак обязательности требования                       |
| 9 | `confidence`        | `Decimal`  | Нет          | Коэффициент уверенности в требовании                    |
| 10| `origin`            | `String`   | Нет          | Происхождение: вручную, LLM, импорт и т.п.              |
| 11| `validatedAt`       | `DateTime` | Нет          | Дата последней валидации                                |
| 12| `rawSnippet`        | `String`   | Нет          | Исходный фрагмент текста (при LLM-извлечении)           |
| 13| `normalizedText`    | `String`   | Нет          | Нормализованная формулировка (при LLM-извлечении)       |
| 14| `requirementType`   | `String`   | Нет          | Предполагаемый тип требования (при LLM-извлечении)       |
| 15| `sourceLocation`    | `String`   | Нет          | Место в источнике: заголовки или диапазон смещений      |
| 15| `extractedAt`       | `DateTime` | Нет          | Дата извлечения требования                              |
| 16| `extractionModel`   | `String`   | Нет          | Название модели LLM, использованной при извлечении      |
| 17| `extractionPrompt`  | `String`   | Нет          | Шаблон запроса, использованный при извлечении           |
| 18| `validationNotes`   | `String`   | Нет          | Замечания и результаты проверок (сводный текст)         |
| 19| `reviewedBy`        | `String`   | Нет          | Эксперт, выполнивший ручную проверку                    |
| 20| `reviewDecision`    | `Enum`     | Нет          | Решение эксперта: APPROVE, REJECT, NEEDS_CLARIFICATION, REWORK |
| 21| `reviewComment`     | `String`   | Нет          | Комментарий эксперта по итогам проверки                 |

**Идентификация и эквивалентность.**  
Идентификация по `id`. Правила эквивалентности не определены.

**Статусная модель (`lifecycleStatus`)**

| Состояние              | Описание                                                  | Разрешённые переходы                                        |
|------------------------|-----------------------------------------------------------|------------------------------------------------------------|
| `EXTRACTED`            | Требование извлечено LLM, проверка не начата.             | PENDING_REVIEW, NEEDS_CLARIFICATION, DUPLICATE, REJECTED    |
| `PENDING_REVIEW`       | Ожидает ручного ревью экспертом.                          | CONFIRMED, REJECTED, NEEDS_CLARIFICATION, DUPLICATE         |
| `CONFIRMED`            | Требование подтверждено экспертом.                        | DRAFT, APPROVED, REJECTED                                   |
| `DRAFT`                | Требование в работе (создано вручную или подтверждено).   | APPROVED, IN_PROGRESS, REJECTED, DEPRECATED                 |
| `APPROVED`             | Требование утверждено.                                    | IN_PROGRESS, DONE, DEPRECATED                               |
| `IN_PROGRESS`          | Реализация требования.                                    | DONE, APPROVED                                              |
| `DONE`                 | Требование выполнено.                                     | DEPRECATED                                                  |
| `REJECTED`             | Требование отклонено.                                     | Завершённое состояние                                       |
| `DUPLICATE`            | Признано дубликатом.                                      | Завершённое состояние                                       |
| `NEEDS_CLARIFICATION`  | Требуется уточнение формулировки или источника.           | PENDING_REVIEW, EXTRACTED                                   |
| `DEPRECATED`           | Требование устарело.                                      | Завершённое состояние                                       |

## 5. Идиомы (паттерны моделирования)

### 5.1. История оценок уверенности

Хранение не только текущего значения уверенности, но и истории оценок.

**Назначение.**  
Поддержать анализ изменения уверенности по мере проверок.

**Диаграмма.**  
Заполняется отдельно.

**Структура.**  
Используется: `ConfidenceAssessment`.

**Бизнес-правила.**
- Оценка уверенности хранится для требования.
- Оценка содержит значение, метод, дату, автора и обоснование.
- Текущее значение `Requirement.confidence` может быть последним или агрегированным из истории.

---

### 5.2. Нарезка документов на фрагменты с метаданными

Хранение исходных Markdown-документов в виде последовательности фрагментов с метаданными для трассировки.

**Назначение.**  
Обеспечить точную трассировку результатов LLM-анализа к конкретному фрагменту исходного документа.

**Диаграмма.**  
Заполняется отдельно.

**Структура.**  
Используются: `SourceArtifact`, `DocumentChunk`, `Requirement`, `TermUsage`, `Constraint`.

**Бизнес-правила.**
- Документ нарезается на фрагменты перед LLM-анализом.
- Каждый фрагмент содержит текст, позицию, иерархию заголовков и хеш.
- Любой извлечённый артефакт должен быть связан с фрагментом.
- При изменении документа фрагменты с изменившимся `contentHash` инициируют перепроверку связанных требований.

**Комментарии.**  
Передача `markdownPath` в промпт LLM критически важна для качества классификации.

---

### 5.3. Канонический термин и алиасы

Разделение канонического термина и альтернативных написаний.

**Назначение.**  
Поддержать синонимы, аббревиатуры и варианты написания терминов.

**Диаграмма.**  
Заполняется отдельно.

**Структура.**  
Используются: `GlossaryTerm`, `TermAlias`.

**Бизнес-правила.**
- Термин имеет каноническое название.
- Термин может иметь несколько алиасов.
- Алиасы используются при автоматическом распознавании.

---

### 5.4. Использование термина с контекстом

Разделение термина глоссария и факта его использования в тексте.

**Назначение.**  
Поддержать трассировку терминов, контекст употребления, уверенность распознавания и ручное подтверждение.

**Диаграмма.**  
Заполняется отдельно.

**Структура.**  
Используются: `GlossaryTerm`, `TermUsage`, `FunctionalRequirement`, `Requirement`, `DocumentChunk`.

**Бизнес-правила.**
- Один термин может использоваться многократно.
- Одно требование может содержать несколько использований терминов.
- Использование термина может быть подтверждено отдельно от требования.

---

### 5.5. Ограничения как отдельный объект управления

Отделение ограничений от требований.

**Назначение.**  
Разграничить требования (потребности) и ограничения (рамки решений).

**Диаграмма.**  
Заполняется отдельно.

**Структура.**  
Используются: `Constraint`, `BusinessConstraint`, `TechnicalConstraint`, `Requirement`, `QualityGoal`, `Risk`, `TechnicalStory`.

**Бизнес-правила.**
- Ограничение не является требованием.
- Ограничение ограничивает требования и цели качества.
- Ограничение порождает риски и диктует технические истории.

---
